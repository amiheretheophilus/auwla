| 2026-10-18 | A written `const` is state like a written `let`; a method chain on an array literal is ordinary state once written. Optimization facts (static lists) never reject code. | User rules: reactivity does not depend on `let`/`const` ("this is not svelte"); normal JavaScript compiles. |
| 2026-10-19 | A component may reassign a prop binding; the write is a local override until the parent sends a different value for that prop. | User called the rejection a bug. The parent owns the prop, so its next different value wins; an unchanged value keeps the override. |
| 2026-10-19 | Rewrite the compiler as `packages/compiler-next/` on branch `compiler-rewrite`, with the same public API; keep the old compiler as a comparison target until the replacement passes acceptance. | User: the current one is "too much depth and unmatainanble"; fixes need "alot of things different places". |
| 2026-10-19 | Layout: a thin `core/`, one folder per concept (props, state, derived, refs, sources, effects, handlers, lists…), fast paths only in `optimize/`, which fall back to the general rule. | User: "refs get their files state, derived state like these things get their files"; "a dedicated folder that will contain an optimization methods … and fall back". |

| 2026-10-19 | `let`/`const` are both state or derived. A binding reassigned later (handler, effect, callback) is state: its first value is a snapshot. A mutated derived object stays derived. | User, quoted in `rules.md` rule 11: "the total first value becomes a snapshot"; on `if (!label) label = …`, "it should work since it somehow being part of a reactivity derivation"; on the mutated `sorted` list, "this is fine". |
| 2026-10-19 | No documented rules for aliasing, in-place `sort` or lost edits: they are plain JavaScript, replayed. | User: "you dont need to write any rule for them because that is how javascrpt works". |
| 2026-10-19 | The UI updates at the end of every synchronous stretch, including before each `await`. | User: "it needs to follow how it will appear in the console". |
| 2026-10-19 | Keep the current names (`memo-dom:`, `mmd_*`, `memoized-dom/*`) for now; the rename to auwla is done later, across all packages at once. | User: "just keep the name we wil do the name changes later". |
| 2026-10-19 | `compiler-next` does not support TSRX. | User: "you can leave tsrx". |
| 2026-10-19 | Priorities are structure and correctness, not speed. The `d6e678b` benchmark is the performance floor; the runtime is kept. | User: "even in this discard codebase we were one of the fastest... what we need is tsructured and correctness". Octane rank 2 of 10 (`compiler/testing.md`). |
| 2026-10-19 | No CI yet: the cases run locally. GitHub Actions on `amiheretheophilus/auwla` comes when the suite reaches thousands of cases. | User: "since these tests are small it okay to run here... once we start building the compiler and start running over 1000's of tests you will see". |
| 2026-10-19 | Emitted code is judged on speed only; readable output is not a goal. | User: "i just need something performant". |
| 2026-10-19 | Loops in the component body replay with the value they build, like `if`. | A loop is another spelling of a derivation (`for … sum += x` = `reduce`); running it once would make behaviour depend on spelling (rule 1). Recommended by the agent; the user moved on to how changes are detected. |
| 2026-10-19 | Whether a body statement changes a value: known methods come from a list in `optimize/methods.ts`; any other call is checked at runtime (deep copy before, compare after), paid only by those statements. | User: "the compiler can contain some optimization lists … if the user uses something we dont know then we have to get a fallback that will make sure we get things correct". |
| 2026-10-19 | Inside `$effect`, `x++` / `x += 1` is a write, not a read: it does not subscribe the effect to `x`. | Agent's recommendation (otherwise every counting effect loops); user: "okay let ride with your answer". |
| 2026-10-19 | compiler-next must beat the old compiler in both correctness and performance, not just match it. | User: "we have to be better than the old compiler both correctness and performance". |
| 2026-10-19 | Old-compiler failures are bugs to fix, never expected failures for compiler-next. JavaScript and the agreed reactivity rules define correctness; the test reference must satisfy them too. | User: "we are not just following the old compiler as in if it fails it doesnt mean it needs to fail here". |
| 2026-10-19 | Finish and verify the reference and wiki before beginning the production compiler. | User: "i dont want you to rush the compiler i just want us to get the refrence and wiki nailed first". |
| 2026-10-19 | An effect's own synchronous writes do not re-run it: its inputs are recorded after the callback returns. `$effect(() => { log.push(node) })` runs once per new `node`, not until the cycle guard. Writes it makes still update the UI and other readers. | The `x++` row above, applied to every write the effect makes (otherwise the same loop happens through a method call).
